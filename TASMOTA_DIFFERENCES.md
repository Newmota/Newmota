# Newmota differences from Tasmota

This document records behavior and architecture that Newmota deliberately changes from
Tasmota. Tasmota remains the primary compatibility reference for every feature Newmota
implements. A feature that has not been implemented yet belongs under current gaps below,
rather than being presented as a deliberate difference.

## Deliberate differences

| Area | Tasmota baseline | Newmota decision | State |
| --- | --- | --- | --- |
| Platform scope | Tasmota also covers ESP8266 and further targets | Newmota requires at least 2 MiB flash and initially targets ESP32, Beken 72xx, Bouffalo BL602, AmebaD/RTL8720D, and RP2350 | Current project scope |
| Feature availability | Tasmota often keeps commands for a broad set of optional drivers | Newmota exposes the commands and data owned by the selected firmware; absent drivers do not receive compatibility-only command shells | By design |
| I2S audio | Tasmota's audio commands and codec selection depend on the compiled target | Optional `USE_I2S` provides native ESP-IDF, Pico PIO/DMA, and AmebaD transports, bounded Berry sessions, and `I2SPlay`, `I2SLoop`, `I2SRec`, `I2SWr`, and `I2SStream`. Audio configurations require at least 4 MiB flash; Beken is deferred and BL602 has no peripheral | Implemented; board qualification open |
| Webcam | Tasmota's `USE_WEBCAM` links every `esp32-camera` sensor driver into the firmware and runs on classic ESP32 boards such as the AI-Thinker ESP32-CAM | Optional `USE_WEBCAM` uses ESP-IDF's DVP controller on ESP32-S3, P4 and S31 boards with PSRAM; sensor drivers are Berry files such as `ov2640.be`. The template functions and `Wc*` image commands stay. Settings live in `/.newmota/webcam.a`/`.b`. Snapshot and MJPEG are both served on port 81. `WcStop` and `WcQuality` are additions; `WcFeature`, `WcAuth`, `WcClock`, RTSP and the classic ESP32 are not available. Berry `cam` keeps Tasmota's `setup`, `get_image` and `info` but runs beside the full driver instead of replacing it; `cam.init()` is not available, and `get_image(img)` needs `USE_BERRY_IMAGE` | Implemented for OV2640; hardware qualification open |
| CSI camera | Tasmota's `USE_CSI_WEBCAM` on the ESP32-P4 calls Berry sensor drivers through a `camera` driver event with a 28-byte struct, and takes the WebRTC offer on its main web server | Newmota ports the pipeline, ISP tuning from `/isp.json`, MJPEG, RTSP/WebSocket H.264, WebRTC and its audio. Sensors register with `cam.register()` and report their mode as members; `WcSession` is stored; the WebRTC offer goes to port 81. The pixel formats follow the P4 revision, so rev 3.x also gives JPEG snapshots during H.264 | Implemented, built for rev < 3 and rev 3; hardware qualification open |
| Ethernet | Tasmota keeps the Ethernet settings in its settings record and Arduino ships its own JL1101 PHY driver | Same commands, EthType numbers, ETH MDC/MDIO/power and SPI pins, `<hostname>-eth` and StatusNET `Ethernet` block. Settings live in `/.newmota/ethernet.a`/`.b`; JL1101 runs on ESP-IDF's generic 802.3 PHY. `EthClockMode` applies to the classic ESP32 only, as in Tasmota on the P4. Safeboot has no Ethernet | Implemented; hardware qualification open |
| ESP-Hosted | Tasmota's P4 builds reach Wi-Fi through an ESP32-C6 over SDIO, take the `HSDIO` template pins, and `HostedOta` streams the companion image over HTTP(S) | Same components and versions (esp_hosted 2.12.13, esp_wifi_remote 1.6.5 on IDF 5.5), the same pins, defaults and `Hosted`, `HostedOta` and `HostedLoad` names. `HostedOta` downloads with `wget` into the filesystem first and is plain HTTP like every Newmota update; `HostedLoad` then streams the file in slices. The device ID comes from the P4's base MAC | Implemented for P4 and P4X; hardware qualification open |
| Filesystem commands | Tasmota uses its `Ufs*` command family | Newmota uses the smaller `df`, `ls`, `rm`, and `mv` commands. There is no shell expansion, piping, redirection, or recursive delete | Implemented |
| SD card | Tasmota's `USE_SDCARD` mounts the card at `/sd` from `SDCard CS` (SPI) or `SDIO CMD/CLK/D0–D3`, makes it the primary file system, and toggles the web file manager between card and flash | Same pins, selection and `/sd` mount point; never formatted. Flash stays the primary file system: `/sd` is a folder in one web tree, `df` reports both volumes, and settings never move to the card. FatFs is vendored (no exFAT). Pins a chip cannot route are rejected with a logged reason; ESP-Hosted's SDMMC slot is never taken. Clock capped at 20 MHz. A restart or deep sleep syncs and unmounts the card. ESP-IDF: SPI and SDIO; Bouffalo, AmebaD and Pico: SPI, plus four-bit SDIO on BL616/BL618DG; Beken deferred | Implemented; hardware qualification open |
| File download | Tasmota's Berry-registered `UrlFetch <URL>` downloads HTTP(S) to the final URL basename | Newmota exposes only `wget <URL>` in Wi-Fi applications. It asynchronously downloads direct HTTP 200 responses with an unencoded Content-Length body and atomically replaces the URL basename (or `/index.html`). HTTPS, redirects, URL fragments, and chunked bodies are unavailable; Safeboot omits it | Implemented; hardware qualification open |
| Command scheduling | Tasmota's `Backlog` queues deferred command execution, with `Delay` and `NoDelay` between its entries | Newmota accepts a bounded synchronous semicolon chain, validates the complete chain first, and executes it in order. `Backlog`, `Delay` and `NoDelay` do not exist; `Defer <ms> <command>` runs one checked command line later, with at most eight waiting | Implemented; hardware qualification open |
| Discovery | Tasmota publishes `tasmota/discovery/<MAC>/config` for its own Home Assistant integration; `SetOption19 1` selects its legacy Home Assistant discovery instead, which standard builds leave out | With `USE_HA_DISCOVERY`, Newmota publishes Home Assistant's own MQTT discovery, one retained `homeassistant/<platform>/<MAC>/<id>/config` per entity: relays, sensor readings, RSSI, signal, uptime, IP address and a Restart button. It needs only Home Assistant's MQTT integration; openHAB and Domoticz read the same format. No `tasmota/discovery`, `Backlog` or `FriendlyName`. `SetOption19 1` turns it off and removes the device; lights and buttons follow | Phase 1 implemented; hardware qualification open |
| I2C scan | Tasmota probes addresses 0x01–0x7f and publishes separate results for active buses | With `USE_I2C`, Newmota scans the shared nonreserved 0x08–0x77 range on its two logical buses. A two-bus result uses one ordered `Results` envelope. Numeric suffixes and payloads are ignored, matching Tasmota | Implemented; host, native build, and hardware validation open |
| Command result framing | Multi-command sequences can produce separate command responses | Newmota returns one JSON object per command request; chains place ordered component results in a `Results` array. Berry `newmota.cmd()` returns the JSON as a map and retains results suppressed with `_` | Berry API implemented; transport framing pending |
| Berry host object | Tasmota exposes a global `tasmota` object with command and garbage-collection functions | Newmota exposes a global `newmota` object with command, GC, millisecond, timer, deferred callback, civil-time, formatting, parsing, and cron methods when time is selected | Implemented; compile and hardware qualification status is reported below |
| Berry `load()` | Loads `.be`, `.bec` and `.tapp` files and removes a stale `.bec` | Loads `.be` files only, with the same name completion and true or false result | Implemented; host-tested, not run on hardware |
| Berry drivers and commands | Tasmota calls `tasmota.add_driver()` instance methods synchronously; `button_pressed`, `button_multi_pressed` and `set_power_handler` can return true to take over the native action, and Rules handle detached switch Actions. `tasmota.add_cmd()` adds commands answered with `tasmota.resp_cmnd*()`; `tasmota.read_sensors()` returns the SENSOR JSON | With `USE_BERRY_DRIVERS`, `newmota.add_driver()`, the `Driver` class, `newmota.add_cmd()`, `newmota.remove_cmd()` and `newmota.resp_cmnd*()` behave as Tasmota's, duck typed per event and without a driver limit. Hooks run from the Berry poll after the event: as in Tasmota, true skips the remaining drivers, but native actions always happen; detach with `SetOption73`/`SetOption114`. The extension `switch_action` receives detached SetOption114 Actions, and `Driver` also declares Newmota's other hooks. `button_pressed` fires on debounced press and release, without Tasmota's raw level and once-per-second repeat. A tick method assigned after `add_driver()` starts within a second. A command response longer than 1024 bytes fails the command instead of being cut. `newmota.read_sensors()` returns the MQTT SENSOR document without `Time`, nil above 1024 bytes, and ignores the display argument. There is no Rules engine | Native compile-tested; hardware qualification open |
| Berry persistence | Tasmota's `persist` module stores dynamic Berry attributes as JSON in `/_persist.json`, saves dirty values before restart, and requires explicit dirty marking for nested edits | Newmota provides `import persist` with JSON-compatible values, explicit or restart-triggered saves, and nested `dirty()` marking. It bounds serialized data to 8192 bytes and 16 container levels, and writes the file in one synchronized LittleFS commit, so a failed save keeps the previous file | Implemented; validation pending |
| Berry scheduling | Tasmota offers timers, cron, blocking delay and Arduino yield | Newmota bounds timers, deferred callbacks, and cron registrations together to 16 callbacks. IDs are strings; duplicate IDs coexist and removal cancels all matching timers or cron entries of the requested kind. Cron uses six local-time fields (second through weekday), requires day-of-month and weekday to both match, skips missed occurrences after forward jumps, and does not replay consumed occurrences after backward/DST fall-back changes. `next_cron` returns the next local epoch, `0` for an unarmed or exhausted registration, and nil for an unknown ID. `delay` accepts 0..50 ms (default 0); delay zero and `yield` use RTOS equal-priority yielding or a 1 ms Pico sleep | Implemented; host and five-family native validation passed, hardware qualification open |
| Native timers | Tasmota persists 16 `TimerN` records and dispatches Action 3 through Rules or a blink fallback | Newmota persists 16 records and global enable state; `TimerN` supports query, partial update, clear, and copy. `Timers` queries only global state. Clock and solar modes use the valid local TimeService clock; `Latitude`, `Longitude`, and `Sunrise` configure solar events. Scheduling starts as soon as the clock is valid; unlike Tasmota, it has no 60-second post-restart guard. Actions 0–2 route through active Power endpoints. Action 3 queues `(timer, output, action, scheduled_local_epoch)` for one `newmota.add_timer_handler(fn)` Berry callback. Without a handler, no script runs. There is no Rules engine or blink fallback. Window offsets are sampled inclusively once per local date and kept within that date; only observed due minutes execute, with no missed-occurrence replay. A local-minute high-water mark plus a consumed-date guard suppresses duplicate firings after clock corrections. Repeat occurrence history is RAM-only, so a restart can repeat an occurrence in the same minute; a one-shot is persisted disabled before action dispatch, so power loss in between can drop that action. Solar times use a compact almanac approximation and may differ slightly from Tasmota; polar dates without a crossing are skipped. For solar timers, `Days` selects the solar event's local calendar date even if its signed offset crosses midnight | Implemented; host checks and five-family native matrix passed, hardware qualification open |
| NTP server selection | Tasmota can fall back to gateway and randomized servers beyond the configured NTP slots | Newmota uses only its three persisted `NtpServer1`–`NtpServer3` slots. Empty slots are skipped; clearing all three disables NTP while retaining the clock. Server changes preserve a manual `Time` hold; `Time 0` releases it. Addresses are limited to 63 ASCII characters and valid DNS/IPv4 syntax | Implemented; ESP32-C2 native compile passed, hardware qualification open |
| Berry date formatting | Tasmota exposes `strftime` and C-style `strptime` conversion | Newmota uses a fixed English, locale-independent specifier subset shared across SDKs; it rejects unsupported directives and out-of-bound formats instead of inheriting libc locale behavior. Formatting has no implicit timezone conversion; parsing returns the civil epoch and unparsed suffix | Implemented; host and five-family native validation passed |
| Berry pixel matrix | Tasmota's native `pixmat` accepts 1–8 bytes per pixel and handles pixel access, matrix blits, and scrolling | Newmota provides a hardware-independent global `pixmat` with 1–4 bytes per pixel or a 1-bit format in the monochrome panel layout, Berry-owned or wrapped byte buffers, checked clipping and overlap behavior, and a packed MSB-first glyph `blit` overload. `buffer()` exposes storage without copying; RGBW packing remains `0xRRGGBBWW` | Implemented; Berry runtime and display behavior remain unqualified |
| Display fonts | Tasmota draws ASCII ST and optional GFX fonts through `DisplayText` and can load `.fnt` files | Newmota embeds compressed Spleen Latin-1 fonts and draws UTF-8 text from the Berry `font` class into a `pixmat`; there is no font file loading | Implemented; display behavior remains unqualified |
| `DisplayText` | Native command with the full `[...]` escape language, including pictures, graphs, touch buttons and rounded rectangles | No native command. `berry/drivers/display/display_text.be` adds the text, position, color and basic shape escapes as a Berry command; `f` and `s` select the closest embedded font instead of scaling glyphs | Berry driver; display behavior remains unqualified |
| Segment and matrix displays | Native TM1637, TM1638, TM1640, TM1650, MAX7219 and I2C backpack drivers with GPIO functions, `DisplayModel` and the `DisplayNumber` command family | No native drivers. `berry/drivers/segment_display` has Berry classes for TM1637, TM1640, TM1650 and MAX7219 with `TmPrint`-style commands; pins are passed to the class and stay unassigned | Berry drivers; display behavior remains unqualified |
| Berry image | Tasmota's `USE_BERRY_IMAGE` `img` class decodes with JPEGDEC and converts and encodes through esp32-camera | Same class, constants and methods with JPEGDEC; the buffer only grows, so `buf_addr` stays valid across same-size frames. RGB888 is R, G, B everywhere, grayscale uses BT.601 luma, region samples outside the image are 0, `from_buffer` checks the length, `convert_to(img.JPEG)` raises (no encoder) and only baseline JPEG decodes. Frames come from `cam.get_image(img [, format])` | Implemented on ESP boards with PSRAM; hardware qualification open |
| Berry Light object | Tasmota's `light` module exposes Light state, setters, and gamma helpers | Newmota exposes global `light.get()`/`light.set()` through the Light owner, uses zero-based endpoint indices, and adds `applied_power` beside requested `power`. `gamma10`, `reverse_gamma10`, and `gamma8` match Tasmota's integer curve and clamp input to their respective ranges | Implemented; timer callbacks remain open |
| STATE | `tele/STATE` and `Status 11` report `Time`, `Uptime`, `UptimeSec`, `Heap`, `SleepMode`, `Sleep`, `LoadAvg`, `MqttCount`, `Berry`, the power and light fields, `Wifi` (`AP`, `SSId`, `BSSId`, `Channel`, `Mode`, `RSSI`, `Signal`, `LinkCount`, `Downtime`), `Hostname` and `IPAddress` | Newmota reports the same fields in the same order and formats, including Tasmota's `RSSI` (0–100 quality) and `Signal` (dBm). `Mode` is reported only on ESP-IDF, the only backend that exposes the negotiated PHY mode; `Band` follows `Channel` (see 5 GHz Wi-Fi). `BSSId`, `Channel` and `Band` appear after the first link refresh, about a second after connecting. `Berry` reports the last collection instead of collecting first, because the snapshot is rebuilt every 100 ms. Uptime, like everywhere in Newmota, comes from a 32-bit millisecond clock and wraps after 49.7 days. Safeboot keeps `UptimeSec` and the power fields | Implemented; hardware qualification open |
| Sleep | `Sleep 0..250` (default 50) sets the dynamic loop sleep; `SetOption60` selects normal sleep and light sleep; `SetOption127` keeps Wi-Fi awake; `STATE` reports `Sleep`, `SleepMode` and `LoadAvg` | Newmota keeps the command, default and dynamic meaning, and serves console and web input during the wait. Values above 50 are stored but act as 50 (`Active` reports it), so 100 ms relay timers keep their deadlines; 10 ms button probes continue during the idle wait. Timing-sensitive work (light fades, addressable strips, open serial ports, BLE, transfers, and builds with I2S, edge capture or a display) keeps the 1 ms loop. `SetOption60 1` selects normal sleep (the full wait after each pass), as on Tasmota ESP32 without light sleep, which Tasmota maps to modem sleep there too. `SetOption127` and `Sleep 0` disable Wi-Fi power saving. Pico 2 W never enables it and Beken, Bouffalo and AmebaD keep SDK defaults. `STATE` and `StatusSTS` report `SleepMode`, `Sleep` (the applied value) and `LoadAvg` with Tasmota's moving average, kept in thousandths of a percent because Tasmota's whole-percent arithmetic truncates the share of NG's sub-millisecond passes to 0 | Implemented; hardware qualification open |
| WifiPower | `WifiPower` sets fixed power in dBm, `1` the chip default and `0` RSSI-based power, reported in `Status 5`. Values above 25.5 wrap around, invalid text selects dynamic, dynamic mode drops to minimum power without a link, and ESP32 rounds the request to whole dBm first | Newmota keeps the command, default, limits and dynamic formula on ESP-IDF builds. Values above the maximum cap at it, invalid text is rejected, dynamic mode uses the chip default without a link, and the request goes to the SDK with quarter-dBm precision. Beken, Bouffalo, AmebaD and Pico builds have no command and keep SDK power | Implemented on ESP-IDF; hardware qualification open |
| 5 GHz Wi-Fi | ESP32-C5 selects 2.4 or 5 GHz automatically. No field names the band: `Channel` (36 and up is 5 GHz) and `Mode` in `STATE` show it, and `WifiScan` lists each network's channel | Newmota selects the band the same way on ESP32-C5 and reports it in the same `STATE` and `WifiScan` fields. It also names the connected band as `Band` (`2.4GHz` or `5GHz`, from the channel) after `Channel` in `STATE`, after the network fields in `Status 5` and as Band and Channel rows on the web Information page, whose SSID row shows the connected network. BW16 (RTL8720DN) uses its SDK's band selection and reports `Channel` but not `Mode`. Other chips stay on 2.4 GHz and report `2.4GHz` | Implemented on ESP32-C5 and BW16; hardware qualification open |
| WifiTest and web Wi-Fi setup | `WifiTest` and the web Wi-Fi setup give a new network 9 s to connect, and the ESP32 core joins the first access point with that SSID it finds | `WifiTest` is the same: 9 s, first access point found. The web and recovery Wi-Fi setup scan every channel and join the strongest access point with that SSID, as a normal connect does; on the ESP32-C5 they allow 30 s, because a join on 5 GHz took about 24 s on hardware | Implemented; hardware qualification open |
| Deep sleep | `DeepSleepTime` on ESP8266 and ESP32 sleeps after each TelePeriod, wakes on multiples of the time, keeps the wake plan and timer slip in RTC memory, honours a `DeepSleep` pin, a `Wakeup` rule with Timers, and SetOption76 | Optional `USE_DEEPSLEEP` ports the command, countdown, network timeout, slip correction, retained `tele/DeepSleep` event, `DeepSleep` pin and SetOption76 to every family. ESP (except the C2), AmebaD and Pico keep the plan between wakes and sleep at most an hour per cycle like Tasmota; ESP32-C2, Beken and Bouffalo keep nothing, so one sleep covers the whole wait (Beken caps it at 36 hours, BL602 and BL702 at 36 hours, BL616 and BL618DG beyond a year) and there is no slip correction. RP2040 cannot power down with a timed wake: it stops all clocks but the RTC and reboots on the alarm. The `Wakeup` rule is absent because there are no Rules. MQTT closes without DISCONNECT, as on restart, so the broker publishes the LWT | Implemented; hardware qualification open |
| Berry ULP module | `import ULP` drives the ESP32 ULP-FSM, the S2/S3 ULP-RISC-V and the LP core; `adc_config` raises on LP-core chips | Optional `USE_BERRY_ULP` (ESP32, S2, S3, C5, C6, P4, S31) has the same eight functions and behaviour. On the P4, `adc_config` uses its LP ADC; the C5, C6 and S31 have no ADC the LP core can reach and still raise `ulp_adc_config_error`. `set_mem`/`get_mem` raise `index_error` outside the reserved ULP memory (4 KiB, 8 KiB on LP-core chips) instead of writing past it. `adc_config` takes ADC1 the same way Newmota's ADC driver does, so the two cannot share it | Implemented; hardware qualification open |
| Berry dashboard widgets | Tasmota's `MI32.widget(html [, cb])` hands one HTML string (with an inline chart DSL and optional scripts) to the next poll of the `/m32` page, and calls the callback on every request to that page | Newmota provides `import widget` with `set(id, html)`, `data(id, value)`, `remove(id)`, `on(id, fn)` and `viewers()`. As in Tasmota the script ships the HTML and any JS; the Home page inserts it as a card, runs its scripts and adds base code: `w2`/`h2` spans (`box` works as the card), `data-v` bindings, `data-chart` charts (`line`, `hist`, `gauge`, `qr`, `matrix`) in place of the DSL, `data-act` controls and `nm.*` helpers. Values travel separately through `data()` and are shown only as text, field values or chart numbers, so names from BLE or the network cannot become markup. Each id keeps its latest markup and data, so late viewers and several tabs see them too. Controls queue `fn(name, value)` for the Berry loop instead of calling the script per page request, and scripts no longer need fetch loops of their own; `viewers()` replaces the hint that the callback only ran while a page was open. At most 16 widgets with 4096 bytes of markup and 2816 bytes of data each; ids are `A-Z a-z 0-9 _ - .` (not `.` or `..`); they are cleared with the Berry VM. The compact Beken page draws only the `matrix` chart and, with `USE_MATTER`, `qr`; it widens cards with `w2`/`w3` but has no row spans and no update highlight | Implemented; hardware qualification open |
| Berry BLE buffer | Tasmota's `BLE.conn_cb(cb, buf)` and `BLE.adv_cb(cb, buf)` take a script-allocated `bytes` buffer that the driver writes through a raw pointer; payloads carry a one-byte length prefix, and an advertisement is address, type, RSSI and length followed by the data | The `BLE` module owns the buffer: `BLE.buffer` is a fixed-size `bytes` object, `BLE.len` the number of valid payload bytes, and `BLE.init(size)` picks the size (default 256, 32–4096) before the buffer first exists. `conn_cb(cb)`, `serv_cb(cb)` and `adv_cb(cb)` take only the callback; passing a buffer raises. Payloads start at offset 0 without a length byte; for a job the script sets `BLE.len` before `run()`. An advertisement is address (6), address type (1) and signed RSSI (1), then the payload from offset 8; `BLE.len` counts only that payload. Active scanning is `BLEActive` instead of `MI32Option4`; `BLEScan` (scan timing) is new, and `BLEWatch` sets the watch list that `BLE.adv_watch` shares. `BLE.info()` has no peer `name`; its debug record adds `adv_drops` and the scan and connection task stack headroom to Tasmota's `queue_drops`. Bond records from `BLE.store()` are per SDK and not interchangeable with Tasmota's NimBLE structs | Implemented; compile-tested, hardware qualification open |
| Berry MQTT module | Tasmota's `mqtt` module publishes strings or bytes and dispatches matching subscription callbacks across reconnects | Newmota conditionally provides `import mqtt` with `publish`, callback-based `subscribe`, `unsubscribe`, and `connected`; it bounds script filters/listeners and follows Tasmota's source behavior for payload slicing. The Berry driver/`mqtt_data` API is not present | Callback API implemented; driver delivery and hardware qualification remain open |
| Status aggregation | `Status 0` publishes separate section responses; `Status0` returns the combined object on `STATUS0` | Over MQTT, both `Status 0` and `Status0` publish separate sections on `STATUS`, `STATUS1` and so on, because the combined object does not fit the 1024-byte MQTT response limit. Elsewhere both return one object containing all status sections, and a request from elsewhere also publishes the sections while MQTT is enabled. Safeboot, whose object fits, stays combined on `STATUS0` | Intentional; current dispatcher |
| Status fields | `Status` through `Status 13` report the full Tasmota field lists | Newmota reports the fields it has a backing setting or measurement for, in Tasmota order. `Status` carries `DeviceName`; `StartupUTC` is derived from the clock and uptime and appears only with valid time; `Sunrise` and `Sunset` are left out on polar dates; `CpuFrequency` and the flash identity fields are left out where the platform cannot report them (flash identity on all but ESP-IDF, the clock on all but ESP-IDF and Pico). Safeboot keeps short sections and has no `StatusMQT` | Implemented; remaining fields are open; hardware qualification open |
| Console results | Serial shows results as timestamped log lines with an `RSL:` label and topic, such as `RSL: RESULT = {...}` | Newmota timestamps each result line on serial and in the Web Console but prints the JSON without a label. MQTT and `POST /api/command` stay plain JSON. |
| Restart reason | `Status 1` and MQTT `Info3` report ESP32 reset text such as `Software reset digital core`, or `Blocked Loop` | Newmota reports `Power On`, `Software`, `Watchdog`, `Panic`, `Brownout`, `Deep Sleep` or `External`, the same on every platform. Where the reason is unknown, `Status 1` leaves it out and `Info3` reports `Power On` or `Restart`. Bouffalo always counts as unknown, and Safeboot `Info3` keeps `Power On` or `Restart`. A blocked loop is not detected | Implemented; hardware qualification open |
| Boot-loop fallback | From the fourth quick restart (SetOption36 offset 1), Tasmota permanently disables rules, shutters, BLE and autoexec in the settings, then clears the user GPIOs, then selects the fallback module, and switches to Safeboot after ten | Newmota skips BLE, Matter, LVGL autostart and `autoexec.be`, and from the fifth also the user GPIO assignments, for that boot only and never changes the settings; the next boot that is not a loop starts everything again. From the tenth it restarts into the paired Newmota Safeboot only, never a foreign recovery image. `Status 1` reports `BootLoop`. SetOption36 is absent; the fallback-module step is open. ESP32-C2 uses ordinary no-init RAM like Tasmota; power-on, brownout and deep-sleep wakes start a new count, and retention across warm-reset paths needs hardware qualification. Other ESP targets require RTC memory. AmebaD uses SDK user backup register 3 with a magic and inverse count; only software and watchdog resets continue a valid count, and ten seconds of runtime clear it. Beken and Bouffalo maintain unqualified diagnostic no-init SRAM counts but keep the guard unavailable; they skip autoexec and never reduce a boot. Bouffalo continues valid records on unknown resets and starts fresh on deep-sleep wakes; no-init placement does not establish power-cycle freshness | Implemented; hardware qualification open |
| Status availability | `Status 6` without MQTT, `Status 9` without energy, `Status 12` without a crash and `Status 13` without shutters return an error | Newmota does the same and leaves those sections out of `Status 0`. `Status 12` and `Status 13` are always unavailable, because crash capture and shutters do not exist | Implemented |
| Status 4 memory units | Tasmota reports StatusMEM measurements in KiB | Newmota reports `Free`, `Heap`, `StackLowMark`, and `PsrFree` in bytes while used-size and capacity fields stay in KiB; unavailable metrics are omitted, and PSRAM appears only when supported and initialized | Implemented; intentional compatibility difference |
| HTTP command endpoint | Tasmota exposes the `GET /cm` interface | Newmota uses authenticated `POST /api/command` through the common command processor | Implemented |
| Browser language | Tasmota commonly selects language behavior through its firmware conventions | Newmota embeds one locale catalog at build time. Protocol names, JSON keys, MQTT topics, and errors stay English | Implemented |
| Normal web product requirement | Web support depends on the selected Tasmota build and target budget | Every network-capable Newmota normal application, including Compact, includes a device-hosted web server and essential browser UI | Design requirement; HTTP+Gzip is current |
| Energy on the web page | Tasmota draws one HTML table with phases as columns, and `EnergyDisplay` and `EnergyCols` choose rotating columns or tabs | Newmota shows the meter as one sensor card with the same rows, numbered per phase, through the sensor routes; only power keeps history. `EnergyDisplay` and `EnergyCols` do not exist, and the card shows energy with at most three decimals | By design |
| Web transport selection | Tasmota may expose more than one web transport through its build options | Newmota embeds one selected web representation per build and has no runtime HTTP/HTTPS fallback | Design rule |
| Settings storage | Tasmota settings and filesystem formats are target and version specific | Newmota owns versioned LittleFS records under `/.newmota/`, kept in two A/B slots with generation, CRC, atomic single-write commit, and write-lock rules | Implemented baseline; migration is separate |
| Hardware assignment | Tasmota maps numeric GPIO functions and Templates to its drivers | Newmota preserves the numeric GPIO namespace and Template shape, then resolves them through typed, architecture-aware topology and fixed-capacity bindings | Implemented baseline |
| GPIO listing | Tasmota can list its complete compiled GPIO name catalog | Newmota's `GPIOs` reports the choices compiled for that firmware; the complete canonical registry remains host-side | Intentional size boundary |
| PWM ownership | Tasmota selects raw or Light handling through SetOption15 | Newmota freezes PWM1–PWM5 ownership, SetOption68 and SetOption37 (split grouping and channel order) until restart, and returns an explicit ownership error for raw access to Light outputs | Implemented |

The internal implementation also differs in ownership: portable application code uses narrow
platform contracts, while SDK types, tasks, native storage, and image operations stay inside
platform adapters. Compatibility lives at the command, data, and device-behavior edges; the
internal driver and build structure is Newmota's own.

## Energy setup

Energy monitoring follows the Module/Template/GPIO setup path, including driver-specific
meter functions and BL0942 RX variants. One active driver owns its native channels.
Beken uses its own architecture pin map; a template must match the actual product wiring.
`EnergyConfig` keeps Tasmota's driver-specific meanings. Energy data lives in its own file
rather than in Settings. Each meter keeps its own calibration and starts from that driver's
defaults. Tasmota shares one set of coefficients that defaults to HLW8012 values, and other
drivers replace a coefficient that still equals one of those values. Newmota keeps every
entered coefficient as it is, and it does not rescale old BL0940 current coefficients.
See the [energy guide](src/app/drivers/energy/README.md) for the
remaining gaps.

## Current gaps that are not deliberate differences

These items are still intended to follow Tasmota or the approved Newmota design once their
implementation and qualification work is complete:

- HTTPS for the normal web service and TLS MQTT. The current Compact slice uses authenticated
  HTTP+Gzip because it is the measured implementation available today.
- The separate Safeboot browser updater, remote update, failed-boot handling, and
  platform-specific recovery qualification.
- GPIO `ButtonDebounce` supports the normal 10 ms filter and logical HIGH/LOW stability flags.
  Application buttons expose single/multi-press and HOLD events, ButtonTopic/ButtonRetain and
  SO73 Action messages. SO1/SO40 hold modifiers, extended SO13 escape, reset and six-press
  Wi-Fi actions remain open. The native 2 ms AC pulse detector selected by values ending in 9 remains open; those values
  are explicitly rejected. Cooperative probes can be delayed by blocking application work.
- GPIO switches support `SwitchMode 0..16`, `SwitchDebounce`, `SetOption114` Actions,
  `SwitchTopic`, `SwitchRetain`, `SwitchText` and switch states in SENSOR and Status 8. AC
  detection remains open (`SwitchDebounce` values ending in 9 are rejected). An out-of-range
  `SwitchMode` value is a command error, where Tasmota reports the current mode. `SwitchText`
  holds at most 15 characters and no quotes or backslashes, so all 28 fit one response. `SwitchRetain OFF` clears the retained keys up to the highest
  configured switch, where Tasmota clears all 32. Switch states take at most half of the
  1024-byte SENSOR document; switches beyond that are left out, logged once.
  Tasmota keeps each switch's hold countdown in one byte, with the SwitchMode 11/12 press flags
  in its top two bits. With the default 50 ms `SwitchDebounce` and a `SetOption32` above 31 the
  count overlaps those flags, so modes 11 and 12 never toggle, and long hold times wrap in modes
  5, 6 and 8–10. Newmota keeps a 16-bit count and separate flags; where Tasmota's count fits its
  byte, the behaviour is the same.
  Above 500 ms `SwitchDebounce`, Tasmota's 0.5 s window of modes 8–10, and a hold time below
  one second (`SetOption32` under 10) in modes 5, 6, 11 and 12, round to zero passes and the
  modes do nothing; Newmota waits at least one pass.
  Modes 11 and 12 still need several handler passes per hold: with a long `SwitchDebounce` and
  a short `SetOption32`, their repeat interval rounds to zero and the INCREMENT repeat stops, as
  in Tasmota.
- Returning from Newmota to stock Tasmota remains a separate optional gate.
- Wi-Fi applications include asynchronous IPv4 ICMP `Ping`; Safeboot omits it. Newmota
  permits one fixed campaign, uses asynchronous DNS, and accepts indices 0–8 (default one;
  zero tries up to four and stops at the first reply). It rejects larger indices, IPv6,
  whitespace, and ambiguous numeric address spellings. Tasmota can keep campaigns for
  multiple destinations and supports IPv6 when selected. Newmota's five-second DNS deadline,
  one-second probe deadline/cadence, busy state through cancellation and delivery, and
  queryable current/last status are deliberate bounds. Results retain numeric counters on
  DNS failure and add an `Error` field. Host tests and native compilation do not qualify
  device reachability or establish a performance advantage over Tasmota.
- Additional Tasmota-compatible drivers and commands whose platform owners do not yet exist.
- TensorFlow microphone integration, camera/audio synchronization, simultaneous network
  walkie-talkie routing, and BLE audio endpoints. The native session API supports bounded
  microphone capture, encoded files/network streams, and configurable I2S input/output, but
  these higher-level consumers do not yet have Newmota owners.
- Berry Light timer callbacks; `light.get()`/`light.set()` cover retained endpoint state and
  synchronous mutations, and the gamma helpers provide pure integer conversions.
- `Module2` and other unfinished compatibility edges.

Platform-specific update and recovery limits are listed under
[support level](tools/newmota/README.md#support-level).

## Berry filesystem listings

Berry `path.listdir()` returns direct-child basenames with a deliberate limit of 128
entries and 8192 bytes of names per call. Exceeding either limit raises `value_error`
without returning a partial listing. Paths use the shared filesystem limit of 191 bytes
and reject embedded NUL bytes.
